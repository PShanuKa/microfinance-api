## 🔄 Plugin Registration Flow

Plugins are registered in `app.js` in this exact order:

```
1. @fastify/env          → Validates .env and exposes fastify.config.*
2. jwtPlugin (custom)    → Registers @fastify/jwt + decorates fastify.authenticate & fastify.authorize
3. requestLoggerPlugin   → Adds onRequest/onResponse hooks for console logging
4. corsPlugin (custom)   → Wraps @fastify/cors with project-specific config
5. swaggerPlugin         → Registers @fastify/swagger + @fastify/swagger-ui
6. prismaPlugin          → Creates PrismaClient, decorates fastify.prisma, handles disconnect
7. @fastify/multipart    → Enables multipart/form-data file uploads
8. globalErrorHandler    → Sets Fastify's setErrorHandler (validation, AppError, Prisma, JWT errors)
9. notFoundHandler       → Sets Fastify's setNotFoundHandler (404 responses)
```

> ⚠️ **Order matters!** `@fastify/env` must be first (plugins depend on `fastify.config`). JWT must be before routes (routes use `fastify.authenticate`).

## ✅ Schema Validation Approach

- **Library**: AJV (built into Fastify) + `ajv-errors` for custom error messages
- **Where**: Defined inline in each route's `schema` option (`body`, `params`, `query`)
- **How**: Fastify automatically validates before the handler runs
- **Custom messages**: Via `errorMessage` property in schema (supported by `ajv-errors`)
- **Error format**: Validation errors are caught by the global error handler and formatted as:
  ```json
  {
    "success": false,
    "error": "Validation error",
    "fields": { "fieldName": "error message" },
    "statusCode": 400
  }
  ```

## ❌ Error Handling Pattern

All errors use the **AppError pattern** via factory functions in `utils/errors.js`:

```javascript
// Creating errors
throw createBadRequestError("Message", { field: "field-level error" });
throw createNotFoundError("Resource not found");
throw createUnauthorizedError("Invalid credentials");
throw createForbiddenError("No permission");
throw createAppError("Custom error", 500);
```

The global error handler in `middleware/errorHandler.js` catches and formats:

| Error Type           | Status Code | Response Shape                            |
| -------------------- | ----------- | ----------------------------------------- |
| AJV Validation       | 400         | `{ success, error, fields, statusCode }`  |
| AppError             | dynamic     | `{ success, error, fields?, statusCode }` |
| Prisma P2002         | 409         | Unique constraint violation               |
| Prisma P2025         | 404         | Record not found                          |
| Prisma P2003         | 400         | Foreign key constraint                    |
| JWT errors           | 401         | Token expired / Invalid token             |
| Default/Unknown      | 500         | Internal server error                     |

## 📝 Naming Conventions

| Element        | Convention              | Example                        |
| -------------- | ----------------------- | ------------------------------ |
| Files          | camelCase.js            | `errorHandler.js`, `s3Client.js` |
| Route folders  | kebab-case              | `non-collection-weeks/`        |
| Route files    | `index.js` per folder   | `routes/auth/index.js`         |
| Functions      | camelCase               | `buildApp`, `generateTokens`   |
| Route handlers | Arrow or async function | `async (request, reply) =>`    |
| DB models      | PascalCase (Prisma)     | `User`, `GroupMember`          |
| DB tables      | snake_case (@@map)      | `group_members`, `audit_logs`  |
| Env vars       | UPPER_SNAKE_CASE        | `JWT_SECRET`, `DATABASE_URL`   |
| Route exports  | Default async function  | `export default async function authRoutes(fastify, opts)` |

## ✅ DO — Patterns That Match This Codebase

1. **Route-level auth**: Use `fastify.addHook("preHandler", fastify.authenticate)` at the top of a route module to protect ALL routes in that module
2. **Per-route auth**: Use `preHandler: [fastify.authenticate]` on individual routes for selective protection
3. **Role-based access**: Use `preHandler: fastify.authorize(["ADMIN", "BRANCH_MANAGER"])` after authenticate
4. **Audit logging**: Create `auditLog` entries for every CUD operation with `action`, `entity`, `entityId`, `userId`, `details`
5. **Pagination**: Return `{ success, data, pagination: { total, page, limit, totalPages } }`
6. **Auto-numbering**: Generate sequential IDs like `C-001`, `G-001`, `L-000001` from the last record
7. **Soft delete**: Use `isDeleted: true` flag (implemented in clients) instead of hard deletes for critical entities
8. **Transaction wrapping**: Use `fastify.prisma.$transaction(async (tx) => { ... })` for multi-step operations
9. **Error factories**: Always use `createBadRequestError()`, `createNotFoundError()` etc. from `utils/errors.js`
10. **Response format**: Always return `{ success: true, ... }` on success

## 🚫 DON'T — Anti-Patterns Found During Analysis

1. **DON'T use `console.log` in route handlers** — the `requestLogger` plugin already uses console.log; route handlers should use `fastify.log` / `request.log`
2. **DON'T access `process.env` directly in plugins/routes** — use `fastify.config.*` from @fastify/env (currently violated in `plugins/jwt.js`, `utils/s3Client.js`, `utils/tokens.js`)
3. **DON'T hardcode secrets** — JWT plugin has fallback `"super-secret-key-change-me"` which is dangerous
4. **DON'T skip response schemas** — Currently no route defines a response schema, only request schemas
5. **DON'T mix auth patterns** — Some routes use route-level `addHook`, others use per-route `preHandler`, and some have no auth at all
6. **DON'T leave routes unprotected** — Settings and non-collection-weeks routes have no authentication
7. **DON'T use raw SQL unless absolutely necessary** — Non-collection-weeks uses `$executeRaw` for bulk instalment shifts (documented exception)
8. **DON'T duplicate JWT libraries** — Both `@fastify/jwt` and `jsonwebtoken` are installed; token generation uses `jsonwebtoken` while verification uses `@fastify/jwt`
